# Internationalization (i18n)

Validator Swipe ships in **11 languages**: `fr`, `en`, `es`, `zh`, `ja`, `ko`, `de`, `pt`,
`ru`, `tr`, `ar`. English is the default.

Everything user-visible lives inside `index.html`, in one JavaScript dictionary named `T`.
There is no i18n library and no separate translation files, which keeps the app a single
static file.

## How the language is chosen

In order of priority:

1. The user's **manual choice** (language dropdown), stored in `localStorage` under the key
   `nimiq-miniapp-lang`.
2. The language reported by **Nimiq Pay** (`window.nimiqPay.language`), if supported.
3. **English** (`en`).

If a key is missing in the active language, the app falls back to the French text
(`t(key)` looks up the active language, then `fr`). Because of that fallback, a missing
key never breaks the page — but it silently shows French, which is why key parity
(below) matters.

## Structure

```js
var SUPPORTED_LANGS = ['fr', 'en', 'es', 'zh', 'ja', 'ko', 'de', 'pt', 'ru', 'tr', 'ar'];
var T = {
  fr: { 'app.delegateSuccess': '…', 'hero.title': '…', … },
  en: { … },
  …
};
```

Keys are namespaced by area:

| Prefix | Area |
|---|---|
| `app.` | The interactive mini app itself (cards, buttons, modals, errors, status) |
| `header.` | Page header |
| `hero.` | Landing hero section |
| `how.` | "How it works" section |
| `faq.` | "Who pays for what" section |
| `tech.` | "Technical integration" section |
| `footer.` | Footer |

In the HTML, static text is bound with attributes and applied by `applyStaticTranslations()`:

| Attribute | Effect |
|---|---|
| `data-i18n="key"` | Replaces the element's content via `innerHTML` (a few values contain `<code>` tags) |
| `data-i18n-aria="key"` | Sets `aria-label` |
| `data-i18n-title="key"` | Sets `title` |
| `data-i18n-placeholder="key"` | Sets `placeholder` |

In JavaScript, dynamic text uses `t('key')`; placeholders like `{validator}` are replaced
by the calling code.

> **Security note:** because `data-i18n` values are inserted with `innerHTML`, the
> dictionary must only ever contain trusted, static text. Never build a `T` value from user
> input, URL parameters or API data.

## The golden rule: key parity

**Every key must exist in every language.** All 11 blocks must contain exactly the same
set of keys. A change to any string means updating all 11 languages in the same commit.

You can check parity from the repository root with plain shell tools (no dependencies):

```bash
langs="fr en es zh ja ko de pt ru tr ar"
keys() {
  awk -v l="$1" '$0 == "    " l ": {" {f=1; next} f && /^    }/ {f=0} f' index.html \
    | grep -o "^ *'[a-z]*\.[A-Za-z0-9_]*'" | tr -d " '" | sort
}
for l in $langs; do keys $l > "/tmp/keys_$l"; done
for l in $langs; do
  if diff -q /tmp/keys_fr "/tmp/keys_$l" >/dev/null; then echo "$l OK"
  else echo "$l MISMATCH"; diff /tmp/keys_fr "/tmp/keys_$l"; fi
done
```

Every line should print `OK`. A `MISMATCH` shows which keys are missing (`<`) or extra (`>`)
relative to French.

Parity of *keys* is not parity of *values*. A second useful check is to look for long
values that are byte-identical between two languages other than by design (for example a
brand name) — that usually means a translation was forgotten in one language.

## Adding or changing a string

1. Add the key to the French block first (French is the reference).
2. Add the **same key** to the other 10 blocks. Machine translation is acceptable as a
   starting point (this project's translations were produced with DeepL); native review is
   better.
3. Use the key in the HTML (`data-i18n="…"`) or JavaScript (`t('…')`).
4. Run the parity check above.
5. Open the page in English and in your language (and a long-text language such as German)
   and check that nothing overflows.

Tips:

- Escape apostrophes inside single-quoted JavaScript strings (`l\'app`), or the script will
  fail to parse and the whole app will break.
- Keep `{placeholders}` (e.g. `{validator}`) unchanged in every language.
- Keep any HTML tags (`<code>…</code>`) intact and only translate the text between them.
- Changing the inline `<script>` changes its hash: an operator must recompute the CSP hash
  (see the [Operator Guide](OPERATOR-GUIDE.md)).

## Adding a new language

1. Add the code to `SUPPORTED_LANGS`.
2. Add a full block to `T` containing **every** key (copy the English block and translate).
3. Add an entry to `LANG_META` (display name and an inline SVG flag) so it appears in the
   language dropdown.
4. Right-to-left languages: the app currently sets `lang` on `<html>` but does **not** set
   `dir="rtl"`, so Arabic is displayed with a left-to-right layout. Full RTL support is
   listed as a future improvement in the [changelog](../CHANGELOG.md).
5. Run the parity check with the new code added to `langs`.

## Translation quality

Non-French and non-English translations are machine-generated and have not all been
reviewed by native speakers. Corrections are very welcome: open a pull request that changes
the affected values (keeping all keys and placeholders) — see [CONTRIBUTING.md](../CONTRIBUTING.md).
